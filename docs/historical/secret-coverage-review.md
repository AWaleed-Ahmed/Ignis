# Secret coverage review

The controller reports bounded reference metadata in optional `fidelity.secret_coverage` format v1. It compares rendered Pod and supported Pod-template references with the successfully applied synthetic fixture inventory. The inventory includes names and key names from the selected fixture set and from bundled Secret documents explicitly labelled `raphael.secret_fixture: "true"`; it never copies Secret values. Required references that are positively missing contribute a named material fidelity gap and make `dependencies_available` false. Optional references and unknown coverage do not make that checklist item false. Missing or incomplete inventory, unsupported forms, malformed references, and truncation are unknown. A workload with no Secret references needs no inventory to establish reference coverage.

Secret values are intentionally preserved only in the existing raw patch/application channels: the `rendered_files` field in the `deploy_revision` response, the full rendered manifest artifact, and `SandboxRecord.rendered_yaml`. The latter two are used by the controller's later observe/validation and artifact workflows; they are not covered by the no-values guarantee. Outside those named raw channels, responses, coverage metadata, logs, and persisted sandbox metadata must contain reference names and keys only, never values. This is a bounded guarantee about the controller's output/persistence paths, not a claim that arbitrary process memory or the raw patch input itself contains no Secret values.

Coverage is bounded to 256 references / 65,536 serialized bytes, 128 applied fixture objects, and 1,024 applied key names. Duplicate fixture Secret names are rejected before application so last-write behavior cannot disagree with the saved inventory.

Review reconciled this implementation with current main (`ece2029`) and preserved per-image digest completeness and restart recovery behavior. Local verification: 62 controller tests and 18 contract tests passed. Service tests cover known-empty selection, failed fixture load, successful inventory application, registry restart and terminal inventory cleanup. Actual Kubernetes consumption is checked by the downstream disposable-kind integration; unit/mock checks alone do not establish that claim.

The schema addition requires a new contract snapshot and coordinated consumers: older closed schemas can reject the new property. The release is `contracts-v1.3.0`; no API for production Secret payloads is introduced.
